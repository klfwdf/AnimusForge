# NPC 主动接触动机改进方案

日期：2026-10-15。状态：DESIGN_ONLY，方案已制定，产品尚未实施。

本方案响应玩家反馈：NPC 主动接触经常围绕缺钱、缺粮、结交或盘问，玩家的身份与经历没有充分成为“为什么来找玩家”的理由。目标是让 NPC 能回应玩家做过的事、寻求玩家提供的专业服务、带来真实机会，同时保留原有需求和政治互动。

## 2. 目标体验与首版范围

首版完成两个实施切片：A 为事件反应与动机多样化，B 为玩家公开服务。两片都完成后，才能称为本方案完整落地。

| 动机族 | 合理触发依据 | 玩家能遇到的开场示例 |
| --- | --- | --- |
| 玩家事件反应 | NPC 可知的近期真实事件，结合关系、阵营和已记录结果 | “听说你打赢了那场仗，我想听听你是怎么做到的。” |
| 专业服务 | 玩家明确公开的服务、NPC 知情、真实需求或适合谈论的事件 | 商人询价买货；医师查看伤兵；术士受邀占卜。 |
| 互惠机会 | NPC 实有可交易资源或真实合作条件，玩家有接受资格 | “我有一批多余的马，你是否有兴趣？” |
| 人际交流 | 现有关系、共同经历、可信话题 | 请教、讨论、慰问、争论；保留问候、追求和亲密互动原有资格。 |
| 困难求助 | 现有缺钱、缺粮、缺兵等检测 | 保留援助与借贷；减少多个求助类型轮流连续打断。 |
| 公共事务 | 现有政策、外交、征募、领地与军团资格 | 保留真实政治来意，不被职业接触挤掉。 |

所有开场只提出一个主要来意。没有证据的感谢、疾病、货物、委托、战果不生成。普通见闻不能被包装成亲历；未知旧事件正文可保留为上下文，不据其关键词自动执行机制。

首版沿用现有 NPC 和接触入口。街头商人主动靠近、村民排队求医、生成新访客，属于后续扩展。商人买卖复用现有交易能力；医师、术士首版完成求诊/咨询/占卜的接触与角色扮演。新增治疗数值结算、预言成真和任务奖励不属于首版，不能将其描述为已支持的执行能力。

## 3. 来意选择：先有证据，再做多样化

建议在 Social 现有目录增加小型动机评估与选择实现，宿主只负责游戏对象快照、扫描、追赶和开场投递。不新建 DLL，不复制三份候选规则。

选择流程：

1. 沿用现有扫描间隔、距离、忙碌/战斗状态、NPC 冷却和接触概率边界；不提高总打扰频率。
2. 每个 NPC 根据同一份只读快照生成合法动机：既有需求 + 可知事件反应 + 已公开服务匹配 + 有依据的互惠机会。
3. 对每类候选计算相关性、时效、已有紧迫度和疲劳。对新旧动机分数统一归一，避免“缺钱 95 分、闲聊 10 分”的天然偏置。原始需求强度保留用于解释与类内排序。
4. 先在有合法候选的动机族之间加权选择，再在该族内选择 NPC 和具体动机。类型或 NPC 数量不累加成动机族权重，防止十种求助压倒一种事件反应。
5. 每族仅保留固定数量的最佳候选（建议 4 个），随现有分帧扫描累计；最终一次抽取，避免为所有 NPC 保留无界候选，也避免先丢掉非最高分动机再声称支持多样化。
6. 没有合法新动机时，原有合法动机仍可触发；都在冷却或不合法时本轮不接触。不会为了凑类型虚构事实。

初始相对权重建议：事件 3、专业服务 3、互惠机会 2、人际 2、困难求助 2、公共事务 2。它们是待回放和实机调校的设计起点，不是固定出现比例。资格、疲劳和现有概率仍然生效。三渠道共享含义与资格，保留各自总频率和可达条件；首次不同时重调所有概率参数。

减少重复采用两层规则：

- 保留已有 NPC 冷却和具体类型疲劳，新增动机族疲劳；“借钱→要粮→要兵”同属困难求助，不作为三个全新话题。
- 最近两次已呈现主动接触均为困难求助时，只要存在其他合法动机，下一次优先从其他族选择；没有替代时不强制封禁合法求助。真正紧急情况仍保留需求，不新增“紧迫度 95 就无视去重”的例外。

## 4. 事件与履历怎样成为动机

由 PlayerNotoriety 的现有 owner 提供只读、过滤后的事件快照，保留 StableKey、ActionKind、日期、可核实实体和结果。沿用 10 日窗口，最多查看 16 条近期事件；选最近且尚未聊过的合适事件，不永远只取最后一条。

首批事件反应覆盖：已记录胜负的战事、已有明确记录的营救/释放、定居点变化及其他能直接映射的行为。实现时按真实 ActionKind 清单逐项接线，未识别类型只可使用中性的“询问此事”，不能猜测胜负、受益人或立场。

NPC 的立场由关系、阵营和参与证据决定：友好者可祝贺，敌对者可质疑，但不能因为玩家有武力就默认“你是威胁”。直接感谢、追责需要实体关联证据；现有条目缺 TargetHeroId 时，只有从权威记录获取对应关系后才能启用，不能靠姓名字符串猜关联。

重大履历主要补充“为何值得请教/合作”的依据：对有可靠结构化记录的内容建立候选；自由文本履历可供开场表达参考。首版不对每个 NPC 扫描全文或调用模型把履历猜成职业、能力、关系。

被选中的事件摘要、来源、NPC 知情依据和动机一起进入开场上下文，不依赖前处理碰巧选中 `npc_major_actions`。这只是本次动机的最小证据，仍使用原三段式请求和知识权限，不把整份履历硬塞进每次请求。

## 5. 玩家职业与公开服务

在现有玩家人设编辑流程中加入可选“公开身份与服务”，随同一玩家人设 owner 的资料保存、导入和导出；不建立另一份全局职业 JSON。实现前核实 LoreRule 序列化与编辑/导入消费者，字段缺失视为未声明服务，原背景原文保留。

首版内置三组稳定服务标识及 CN/EN 显示文本，可多选；另带玩家自定义显示名称和简短服务描述。名称与角色扮演内容可自定义，实际可执行能力仍由已接线的标识决定。不会只因医学/交易技能较高就擅自认定玩家以此为业。

| 服务 | 候选资格 | 首版结果边界 |
| --- | --- | --- |
| 商品交易 | NPC 确有采购需求和资金条件；玩家当前可交易库存有匹配货物；NPC 已知道其身份/服务 | 询价、购买意向，后续成交走真实交易执行器；再验库存、金额与权限。 |
| 医疗咨询 | NPC 本人或所属队伍确有伤情；NPC 知道玩家公开行医 | 请看伤、询问疗养、商谈诊金意向；不开口就扣钱、治疗，不虚构具体疾病。 |
| 占卜咨询 | 玩家明确公开该服务且当前设定允许；NPC 有可知的出征、婚事等顾虑 | 询问吉凶、解梦或求建议；预言是角色表达，不写成已经发生的事实或保证结果。 |

“公开”表示玩家愿意让别人知道，不等于全世界立即知情。首版复用认识玩家/允许人设注入的边界，不新增广播名声。没有公开服务的旧角色仍能通过切片 A 获得事件互动；想稳定获得职业来访，可在现有人设入口填写一次。

自由背景自动推导服务可以后续独立设计；本方案不隐式引入额外模型请求或静默改写玩家人设。

## 6. 三渠道、会话和重复回执

- 地图主动接触：替换候选选择部分，复用现有追赶、遭遇目标、原生/场景开场路由。
- 主动来信：接入同一动机资格与证据，保留现有情感、自身事件、需求和外交类型；医疗等不能远程执行的效果明确排除。旧信件无需重生成。
- 同伴主动聊天：保留现有玩家事件动机，接同一事件标识与去重记录，避免同一件事刚当面说完又发信；保持队内见证资格。
- 玩家后续回应：仍走原前处理、主回复、后处理与事实写入。玩家拒绝、忽略或接受咨询都不自动等于资源交换、关系改变或治疗完成。

建议由 Social 的现有主动接触 owner 维护跨渠道回执，渠道只报告呈现结果。候选至少携带 `MotiveId`、`Family`、`SourceKey`、`Evidence`、`AllowedChannels` 和来源版本；这些是设计字段，不代表仓库已有类型。

同一 `NPC + SourceEventKey` 在事件有效期内只主动谈一次，不允许改成“祝贺/请教”绕过去重。建议同一事件全局最多 3 名 NPC 主动提及，作为可调校的首版内部常量，避免全世界排队评论同一场胜利。职业请求使用 NPC、服务和实际需求的稳定键；不得用每小时变化的血量/库存数字制造无限新键。

会话启动时暂占该键；开场真正呈现后才确认已讨论回执。信件在玩家能看到/收到内容的既有通知边界确认，不在后台开始生成时确认。失败、取消、过期释放暂占，保留原失败节流；玩家主动关闭已经呈现的通知视为本次已打扰，不马上换渠道补发。既有 hero/global 冷却的记录时机单独保留，不混成“模型成功”的新定义。

读档恢复待处理会话与暂占；清理孤立暂占只在加载或已有扫描边界。普通流式开场在首段真正呈现时确认，生成失败但已显示内容不重复重发。

## 7. 资源、设置、性能与存档

- 扩展原 `ProactiveNpcRequestPrompts{,.en}.json` 及实际 reader：每个新增动机具备当面/来信/适用同伴意图，固定字段和语义成对。需要事实模板时使用稳定键与参数；不要求模型固定用包语言回复。
- 保留既有 30 个 NeedType 身份、存档键和用户自定义内容。新类型接通 NormalizeNeedType、session import、提示词 fallback 和所有渠道映射，特别验证读档后不会被降成 FoodShortage。
- 新增一个终端“丰富主动接触”总开关，建议默认开启；关闭后恢复旧候选选择规则，并在旧 session owner 的安全取消边界停止尚未开场的新动机会话，保留已呈现历史与已投递信件。MCM 属性仅作原持久化 owner，不增加 MCM UI。职业服务沿玩家人设 owner 保存。
- 不新增逐帧网络请求、文件读写、全文扫描或反射。事件快照按事件版本和游戏日期失效；人设服务按保存/导入版本失效；NPC 知情和实际库存/伤情在主线程读取，最终发起时再次检查。
- 沿用每批最多 16 支部队、目标 45 帧和当前 1.5 ms 扫描预算检查；这些是现有码的软预算，单个候选仍需测量，不能宣称硬实时保证。新增循环最多 16 条事件和有限服务条目；资料共享缓存，背景任务只接收脱离游戏对象的数据。
- 新回执与字段复用原 `_af_proactive_npc_request_state_v1` 的分块保存，保持旧字段/键/类型；回执按过期日清理并设有界容量，容量满时本轮不再为新事件建接触，不通过淘汰仍有效回执制造重复。服务资料按原玩家人设持久化路线维护，不另写存档字符串副本。
- 字符串分块遵守 CampaignSaveChunkHelper 与现有目录；新增字段/键及真实消费者同步登记 persistence-catalog。旧档缺新字段正常为空，损坏分块不当成成功空状态。

## 9. 验收用例与可观察证据

1. 玩家最近获胜：知情友好 NPC 可选祝贺/请教，未知 NPC 不泄露事件；无胜负证据不编造胜利。仅为旁观者时不能声称“你救了我”。
2. 玩家是商人且有粮：缺粮、具备交易条件的 NPC 可来购买，既有交易后处理收到相同规则与物资事实；说“买了”但未执行时不写成交 AFEF。
3. 玩家是医师：有伤员且知情才来求诊；无伤员不虚构瘟疫，拒绝后不会立即换信使重复求医。只验收咨询时不能报告治疗已实现。
4. 玩家是术士：明确服务与合理顾虑才可来求占卜；未声明服务、未知身份不选；不把预言记成历史事实。
5. 连续两次困难求助且有合法替代：第三次选择其他族；没有其他合法动机时仍能正常求助。政治/外交、亲密关系等原资格不放宽。
6. 同事件当面已呈现，随后来信/同伴不会重复；未呈现的生成失败、取消或读档不会永久吞事件；既有通知关闭语义可追溯。
7. 旧档、旧会话、未知新类型、禁用开关、CN/EN 导入导出、分块损坏分别回放；正常旧 NeedType 不变，新类型不能落成 FoodShortage。
8. 在固定候选、各族合法的可重复模拟中验证权重与频数，增加求助 NPC 数量不能使求助族权重成比例膨胀。记录真实游戏可用候选比例；不要求所有世界状态达到固定百分比。
9. 对比同一候选规模下扫描耗时/帧、总耗时、分配、缓存命中与模型请求数；无逐帧 IO/额外模型请求。相较基线若有可见卡顿，定位新增工作并修复后验收。
10. 扩展 `tests/replay/PhaseEightParityReplayTests/` 的资格、候选、冷却、开场和 session 生产源码回放；新增选择/知情/跨渠道呈现测试。持久化改动运行 PersistenceChunkReplayTests 与 `validate_persistence_profile_config.py --chunk-contract-only`，执行官方双 API 构建。
