## 2. 只增加两类来意

| 新来意（拟定标识） | 资格与材料 | 表达示例 |
| --- | --- | --- |
| 玩家经历交流（PlayerHistoryDiscussion） | NPC允许知道玩家履历，已有MajorSummary非空，并且未处于履历交流冷却 | 听闻玩家的征战经历而来请教；对其过去的抉择感到好奇；结合立场讨论这些经历。 |
| 玩家近况反应（PlayerRecentEvent） | NPC允许知道该近况，事件在有效窗口内且尚未向该NPC呈现 | 最近获胜后祝贺或请教；遭遇失败后慰问或质疑；针对真实记录的营救、释放、领地变化来询问。 |

只读现有记录，不增设职业字段、职业识别、服务菜单或独立机会生成器。与经历有关的合作可以自然谈及，后续机制仍走既有规则，不凭来意生成任务、奖励或能力。

长期履历不能被遗漏为“只给正文补背景”：只要知情且有履历，就能建立独立的经历交流候选。因为MajorSummary本身是文本，首版不要求先把它变成结构化事件；候选确定“来谈玩家过往”，再让现有开场模型根据这一份受限履历自然选择具体谈法，不增加单独的意图生成请求。

近期事件优先使用StableKey、ActionKind和已记录结果，最多检查原窗口内16条，选择适合当前NPC且未聊过的材料。未知类型可以中性询问，不猜测胜负或受益人。没有直接关联证据时说“听说你救了人”，不能改成“谢谢你救了我”。

NPC立场结合现有关系、阵营和可核实关联。友好者不必一律恭维，敌对者也不必一律把玩家当威胁；提示词允许好奇、请教、关心或质疑，并要求依据材料表达。一次开场只围绕一个主要来意，不强行落回借钱求物。

## 3. 怎样进入选择阶段

1. 复用当前扫描、距离、忙碌状态、NPC与全局冷却，不提高总接触频率。
2. 同次扫描保留两组候选：现有动机组、玩家经历/近况组。现有组内部继续使用原资格和排序；新组按知情、时效、关系相关性与重复情况筛选。
3. 两组都有合法候选时，先在两组之间选择，再选NPC与具体来意。初始建议等权作为回放调校起点；这是有候选时的选择权重，不是承诺实际一半接触来自新动机。总触发概率仍受原渠道门禁约束，不把两组独立触发相加。
4. 每组只保留有界候选，复用原分帧扫描。旧需求类型或NPC数量不能直接累加为组权重，避免大量缺钱候选淹没一条有效事件。
5. 只有一组合法时使用该组；无可知履历/近期事件时沿用旧来意，不虚构新材料。不要先按原最高分丢掉事件候选，再做所谓多样化。

本次不重构六类动机族、不新增全局权重面板，也不另加职业或丰富模式开关。使用已有主动接触/来信/同伴开关；保留既有需求检测、政治关系限制和旧类型疲劳。

## 4. 开场证据与三渠道

选中时固定来源、来意及当时可知的证据：经历候选携带原有长度限制下的履历，近况候选携带具体事件摘要。资料在进入请求前按现有知情边界再次核对；不依赖前处理碰巧选中npc_major_actions。

- 地图接触：新来意进入现有追赶、遭遇与开场路由；同时覆盖原生自由对话和场景开场消费者。
- 主动来信：接入相同的履历/事件资格与证据，保留原情感、自身事件、需求和外交来信。已经生成的旧信件不重写。
- 同伴：复用现有PlayerRecentEvent，接共享来源键和呈现回执；经历交流使用相同知情规则，保留队内见证权限。
- 玩家回应：继续走现有前处理、主回复、后处理及记忆链路。接触、请教或慰问本身不意味着承诺、交易或关系变化，游戏动作只记录真实执行结果。

只共享动机判断和证据，不复制私有请求体、标签解析器或历史格式。CN/EN预设、事实模板、reader、最终messages及渠道映射在同一实施切片完成。

## 5. 避免重复

近期事件用NPC ID + SourceEventKey去重，同一NPC不能刚当面谈完又寄信重复；不能通过将“祝贺”改成“请教”绕过。跨NPC保留来源疲劳，减少多人接连评论同一件事；参数沿现有冷却口径在回放中调校，不把任意硬配额作为完成前提。

长期履历采用NPC级的经历交流冷却，建议初值30游戏日。文本版本变化只使缓存失效，不重置交流冷却；不能因履历自动改写或用户改一个字就当成全新事件。这个初值是方案建议，不是实机结论。

候选选择后暂占来源，真正呈现才确认已讨论；沿用现有渠道通知边界，明确生成失败、取消、过期与已呈现后关闭的区别。保留原hero/global冷却时机，不混为一谈。回执跨渠道共享，由Social的现有owner负责，渠道只报告结果；加载时恢复待处理会话，避免吞事件或重复开场。

## 6. 性能与存档

- PlayerNotoriety owner提供只读快照；履历按内容版本缓存，近期事件按事件版本/日期失效，知情按现有owner检查。游戏对象读取在主线程，不新增每帧全文扫描、IO、反射或模型请求。
- 每个候选最多检查16条近期事件，履历使用现有长度上限；复用16支部队/批、45帧目标和1.5ms软预算，实际额外开销必须测量。
- 保留原30个NeedType身份、原存档键及字段。新类型完整接入NormalizeNeedType、session import、预设fallback与渠道映射；读档不得误变成FoodShortage。
- 有界回执/冷却复用原主动接触owner的分块保存路线；按扫描/加载边界清理过期项，不另存一份完整玩家履历。旧档缺新字段按兼容默认加载，损坏分块不当成成功空状态。
- 持久化新增字段及消费者同步登记现有目录；未知旧文本保留原值，不依靠全局替换或猜译。

## 7. 近况采集与 token 控制

### 数据与调用次数

复用PlayerNotoriety现有事件监听和外部行动写入入口。本地记录近况、去重、筛选候选不调用模型，采集本身消耗0 token；不额外逐NPC询问模型“他该为什么来找玩家”。原有长期履历摘要生成如有模型调用，其费用仍然存在，本方案不新增或加频此流程。

既有近期记录窗口为10游戏日、最多96条；候选评估最多检查16条。事件包括已有接线的俘虏处置、获释、停留休息、招兵、竞技/棋局结果及其他机制确认的行动。本次直接复用已覆盖数据，不承诺所有玩家行为都已采集；缺失事件先登记，不为了丰富来意补造记录。

### 每次只围绕一份材料

- 近况开场：选1条事件，建议证据正文100–250个中文字左右；保留时间、人物/地点、动作、结果、否定和不确定性。该区间是编排目标，不是按字符数保证的token上限。
- 履历开场：选现有履历里一个完整片段，建议200–400个中文字左右，并服从现有履历上限。按原句边界提取、保留必要上下文，不另用模型重写摘要；若片段截取会改变因果或人物关系，改选其他可完整表达的材料，原存储不裁切。
- 每次一类来意，加入简短意图说明；没有必要同时附整份履历和整页近况。开场输出沿用原长度规则。
- 普通玩家后续对话保持现有记忆/检索能力，不能为了节省这次开场的token删掉后续所需事实。

### 在组装处去重

现有公共上下文在`PromptContextCaptureBannerlordAdapter.cs:140`组装ResidentRecentActions，主动来信在`CourierDeliveryBehavior.PromptPreparation.cs:292`再次补充玩家近况；原生开场的routingInput也包含开场事实。因此“新增一条”不能直接等于“整轮只增加一条的费用”。

实施时在当前主动开场的共享上下文组装入口，用SourceEventKey标记选中事件，证据正文只保留一份，意图引用同一可读事实；履历片段避免在主动意图与npc_major_actions块中重复。模型请求必须有实际可读证据，不能只发送无法解析的ID。同一请求内避免重复，不宣称不同模型请求能共享上下文而免计费。

保留其他既有必要上下文；不以全局删掉16条近况来制造节省。为解决重复注入而修改消费者时，只限主动开场路径并对三渠道核对，勿覆盖其他并行记忆/快报修改。

### 成本预期与测量

此前150–500输入token只能作为短近况材料在**一个包含该新增块的请求**中的粗估，分词、姓名、英文及格式均会改变数量；长期履历通常更多。如果三个阶段都各新增同量材料，整轮示例可能为450–1500输入token，而非150–500。实际也可能复用现有内容、只在一部分阶段新增，必须测量后确定。

采用同一NPC、同一历史、同一设置的基线/改后请求对照：记录前处理、主回复、后处理和实际重试的请求数与usage，分别合计输入、缓存输入和输出；没有provider usage时只报告本地估算与文本长度，不冒充实际账单。新增动机不新增意图规划调用，总接触频率也不调高；不保证输出长度或总费用完全不变。

金额按所用模型的实际费率计算：各请求未缓存输入、缓存输入和输出分别计价后求和。尚无目标模型usage测量，本方案不给固定金额承诺。离线阶段先验证请求数量和材料重复；真实usage与开场质量在实际模型验收时一起检查。

## 8. 优缺点与取舍

| 优点 | 依据或限制 |
| --- | --- |
| NPC会回应玩家实际经历，减少主动接触只有索取的感觉 | 新材料参与候选选择，选中事实直达开场，而非仅改变求助措辞。 |
| 玩家无需新增填写资料 | 复用现有履历和近期行动；记录空白时仍走旧动机。 |
| 成本相对可控 | 本地筛选、无额外规划调用、单份材料和组装去重；实际增量需按整轮usage验证。 |
| 能保持既有玩法连续性 | 复用三渠道、动作执行器、存档owner与原30类身份。 |

| 缺点/风险 | 处理及仍然存在的限制 |
| --- | --- |
| 新互动占用原接触机会，原求助或政治来意会减少 | 总频率不提高，初始两组等权只供调校；必须查看原有重要动机的实际出现情况。 |
| 可能多人反复议论同一件事，长期履历更易空泛 | 同事件跨渠道去重、来源疲劳、履历冷却；模型文风与趣味仍需实际体验检验。 |
| 已记录与NPC应该知道并非一回事 | 沿用知情边界并限制直接关联断言；现有知情模型较粗，本任务不扩成精细传闻传播系统。 |
| 内容受采集覆盖和履历质量限制 | 不把无记录行动或自由文本推断成确凿机制事实；未知类型采用中性来意。 |
| 代码筛选不能充分理解任意自由文本 | 长期履历候选先定为交流过去，再由原开场模型选具体表达；可控且省调用，但个性化精细度有限。 |
| 输入token、响应时间和兼容工作有所增加 | 限定材料、测整轮usage，验证读档和重复回执；不能以“采集0token”承诺全流程免费。 |

推荐采用这一版：先接已有数据和两类来意，用本地筛选控制成本，再通过真实开场验证效果。首轮不增加职业、服务、独立商机或额外模型规划。

## 9. 实施顺序与验收

A. 补齐履历/近期事件只读快照、两类来意及选择逻辑，接入三渠道与CN/EN开场证据。

B. 接通跨渠道回执、履历冷却和旧档兼容，完成专项回放及官方1.3/1.4与Bootstrap构建。

C. 用真实模型与实机确认“为什么来找玩家”确实改变，并记录候选、频数、扫描开销和整轮token增量；离线通过与实机通过分别报告。

必要验收：

1. 只有长期履历、没有近期事件时，知情NPC仍能专门来谈过去；不要求玩家新增填写资料。
2. 有近期胜利/失败/其他事件时，来意围绕该事件，结果和立场有据；不知情NPC不泄露记录。
3. 履历与近况都为空时，既有求助、关系、外交资格正常工作；不编造新经历。
4. 新旧候选同时存在时，两组都有选择机会；增加旧求助类型不能成比例挤掉经历组。校验可重复抽样和真实可用候选比例，不要求所有存档达到固定频数。
5. 同一NPC跨当面/来信/同伴不重复同事件；履历文本改写不会重置冷却；失败/取消/读档与已显示内容分别回放。
6. 新旧会话、全部新类型、关闭现有入口、分块损坏与CN/EN最终messages均有针对性验证。
7. 扩展现有PhaseEightParityReplayTests的资格、候选、冷却、开场与session生产源码回放；持久化变更运行PersistenceChunkReplayTests及validate_persistence_profile_config.py --chunk-contract-only，使用原官方双版本构建入口。
8. 对比相同候选规模下扫描耗时、分配、缓存命中与模型请求数；实际开场不能把每次事件反应又写成借钱或结交。
9. 对照三渠道最终请求，检查选中材料的重复和完整性；一次接触按实际发生的所有阶段汇总usage，区分有数据实测与字符/分词估算。无新增意图规划调用，无全局削减既有记忆上下文。

实施时每片先建本地检查点、验证后提交；本方案不授权打包、部署、推送。调试记录来源键、来意、知情、候选及呈现结果，复用现有日志节流，不输出整份私人履历。
