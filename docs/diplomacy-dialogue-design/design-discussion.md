# 外交对话与宣言衔接设计访谈

日期：2026-10-02。范围：功能设计，尚未授权实施；当前工作区已有改动均保留。玩法访谈已收敛，完整方案见 [DESIGN.md](DESIGN.md)。

## 用户目标

让统治者发布外交宣言时能够使用自己的经历和与玩家的交往材料；使玩家通过交流影响统治者的外交立场、宣言内容及发起宣言的意愿，补齐口头外交与宣言外交的衔接。

## 当前源码证据

- `WorldDiplomacyBehavior.cs:2248` 的 `BuildLlmMessagesForJob` 为宣言生成组装任务规则、外交长期档案与本次任务材料。
- `WorldDiplomacyBehavior.cs:11867` 的 `AppendDiplomaticAuthorDecisionContext` 提供国家局势、人格背景、制度声音、亲属及政策材料；`12563` 的 `BuildRulerVoiceContext` 调用人物人格与背景接口。
- `WorldDiplomacyBehavior.cs:10579` 的共享对话 prompt 补充入口，在话题或资格命中时将该人物已知的外交材料注入普通交流。
- `DiplomacyBehavior.cs:170,248,292,322,360,387` 将已执行的口头外交结果通知世界外交系统。
- `WorldDiplomacyBehavior.cs:10278` 将此类结果记为 `oral_diplomacy` 公文，标记实际已执行、无需答复，并传播结果。这个入口负责已发生结果，不能视为未来宣言的劝说入口。

- 当前 `WorldDiplomacyBehavior` 对 `MyBehavior` 的调用未使用个人对话历史、未压缩记忆或个人压缩记忆读取接口。人格接口只读取人物的 Personality/Background，不隐含个人记忆。
- 宣言进入外交档案与周报材料；这不等同于直接写入该统治者的个人对话历史。
- `AnimusForge/ModuleData/RuleBehaviorPrompts.json:741,745,749` 已允许非国王玩家劝说 NPC 统治者向第三国宣战；`DiplomacyBehavior.cs:149-170` 校验后立即执行宣战并通知结果。因此缺失的是交涉影响未来宣言的稳定路径，不能概括为玩家完全无法劝说。
- `AnimusForge/ModuleData/RuleBehaviorPrompts.json:723-725` 的公开外交讨论规则允许评论和建议，但禁止替国王承诺或执行，且后处理规则为空。设计需要区分外交讨论与统治者本人作出可执行安排的资格。

以上证据基于当前 E 盘工作区，不代表其他工作树或玩家正在运行的 DLL。现有结果桥接已经存在，缺口主要是个人材料进入宣言决策，以及尚未执行的交涉意向进入未来宣言安排。

## 方案方向与实现建议

1. 宣言决策按当前统治者读取个人记忆与对话材料，与外交档案共同提供决策依据。
2. 普通交流区分玩家建议、统治者考虑、明确承诺及已执行结果；经资格校验的明确承诺可形成待发布的外交安排。
3. 公开发布与执行结果回到人物可读取的同一记忆体系；私下交涉不自动变成各国共享的公开事实。
4. 延用三渠道共享链路、统一动作校验；新事项经宣言路径处理的明确安排直接创建新的外交回合，接受已存在的正式原案则回到原案所属回合正式答复。玩家亲自即时口头宣战与独立家族停战保留例外。多回合共存的底层改造由另一任务负责，本设计只定义衔接需求，不承担调度底层重建。
5. 材料在生成任务时按人物与外交对象检索并限定预算；避免逐帧扫描全部人物历史。具体缓存、触发频率与失效条件待语义确认后设计。

## 已确认的设计要求

- 既有口头外交也要改造，不能只新增记忆注入而保留当前割裂的玩法。用户指出口头外交跳过宣言，与依靠宣言运行的外交系统不连贯。
- 任何能够接触统治者的玩家均可尝试劝说。身份、信任、既往经历与国家利益影响接受程度；尝试劝说与代表国家签约的权力分别判断。
- 允许与当前议题相关的私人经历、情感和私人承诺影响统治者取舍；按相关性读取个人材料。
- 同时采用两种影响程度：日常交涉作为记忆影响未来判断；统治者明确接受具体外交事项后，形成可追踪的外交安排，进入宣言处理流程。用户已确认这一组合方向。
- 常规新事项流程已确认：玩家建议 → 统治者考虑、拒绝或接受 → 接受后形成安排并创建新外交回合 → 发布宣言 → 按外交规则回应和执行 → 结果回到记忆。已有正式原案的回应与即时例外见 Q11—Q13。
- Q4：接受建议后直接创立新回合，该建议引出的外交事件属于此新回合。用户计划另行改造为多回合共存；本任务不承担这一底层改造，也不能将此要求替换为等待正常周期或覆盖既有事件。
- Q5：明确承诺原则上落实；局势重大变化或约定条件未满足时可以延期、修改或撤回，必须记录原因并供玩家追问。“会考虑”仍是自由判断。
- Q6：默认保护私下交涉细节，公开事迹可引用，明确保密的信息不直接披露。玩家提供的未经证实消息保留其来源与未证实性质，不冒充系统确认事实。
- Q7：玩家端正式外交宣言只能由玩家自己发布；系统不得替玩家写宣言。玩家为国王并与对方国王口头谈妥和平条件后，应由对方国王在新回合正式提出约定条件，等待玩家正式接受；口头同意不能替代玩家正式接受。
- Q8：一次覆盖现有口头外交动作，常规路径为口头答应 → 宣言 → 外交行动，不只首期做宣战与议和。用户同时明确即时口头宣战可以不经过宣言，例如玩家对别国口头宣战；该例外不能被常规流程覆盖，主体区分见 Q11。
- Q9：重复确认同一事项不新建回合，继续已有安排；新的明确条件作为修改或新的交涉处理，不能靠重复答应创建相同事件。
- Q10：尚未公开的安排不由新任国王继承；原统治者死亡或失去统治权后，相关私人承诺终止，而不是自动交给继任者再评估。旧承诺保留为玩家与原统治者的历史，不抹除其记忆；已公开提案与已生效国家协议不归入这一私人承诺终止规则。
- Q11：用户接受所推荐的主体区分：玩家以有权身份亲自当场宣布宣战，可即时执行；玩家劝 NPC 国王接受未来宣战安排，走新回合与宣言流程，不因口头答应而立即执行。
- Q12：接受已有正式提案，在原案所属回合发布正式回应；谈出不同条件时创建新回合提出新方案。用户特别指出第三国劝说和多个相关回合并存场景，要求避免错误归属；具体匹配规则见下方设计。
- Q13：独立家族停战保留现有即时机制，不扩展为家族公文外交，不做额外大改。
- Q14：国家吞并、朝贡国、卫戍国和附庸国谈判一并接入，并支持直接通过发布外交宣言达成这些外交行为；不只是将口头结果登记为历史。NPC 私下接受 → 正式提出约定 → 玩家自行正式接受 → 机制执行。
- Q15：多个有效原案且口头上下文不能唯一确定时，由 NPC 在交流中追问；澄清前不正式回应、不执行、不猜测最新或最早原案，也不为歧义另建回合。
- Q16：吞并与臣属面向任意合法王国组合开放，包括 AI 对 AI，以及玩家主动向 NPC 提出臣属。双方均须正式同意；玩家自己的正式表态仍由玩家亲自发布，不固定玩家王国为接收方或宗主。

## 访谈收敛

Q1—Q16 的玩法决定已逐轮确认。发文前修改按已确认的承诺和新条件规则处理；公开公文保留历史，后续变更通过新的正式文书表达，不能回写旧公文或把待处理事项标成已执行。接口命名、缓存预算和实现拆分属于工程方案，详细建议与验证标准见 DESIGN.md。

边界核对：`DiplomacyBehavior.ProcessDiplomacyTagsInternal` 的核心动作包括宣战、国家和平、独立家族停战、结盟、解盟、贸易和取消贸易。独立家族停战使用 `Clan` 对 `Kingdom` 的执行入口，不适配现有双方均为王国的公文接口。另有 `KingdomAnnexationBehavior` 的国家吞并，以及 `VassalageBehavior` 的朝贡、卫戍、附庸条约，均可由对话标签直接产生实际效果，必须明确是否属于“现有口头外交”的范围。

Q16 源码事实：吞并入口固定要求接收方由玩家统治（`KingdomAnnexationBehavior.TryAnnexKingdom`）；口头三类臣属入口 `TryCreatePlayerVassalage` 固定玩家王国为宗主。`NpcTributeVassalageBehavior` 已支持 AI 对 AI 的朝贡，但没有同等的 AI 卫戍／附庸入口。世界宣言当前支持动作表未包含吞并或臣属；需要新增正式提案、条件、接受及执行映射。渠道接入与开放新的国家组合是不同设计决定，不能将前者默认为后者已经授权。

实现安全要求：提示词中的资格限制不能代替执行端权限校验。即时宣战及单方解除安排都要明确实际决定者和其当前权限；不能仅凭两个王国 ID 或 NPC 的同意推断玩家已经授权。本轮只记录检查要求，不修改执行器。

存档恢复、失败反馈、条款一致性与记忆回写的工程约束见 DESIGN.md。总体衔接决定见 `docs/adr/0001-dialogue-to-declaration.md`；新回合和玩家发文边界见 `docs/adr/0002-new-event-and-player-authorship.md`；原案路由与王国组合范围见 ADR-0003、ADR-0004。尚未授权实施。

## 给后续多回合底层任务的接入需求

当前 `WorldDiplomacyStorage.ActiveRound` 为单值（`WorldDiplomacyBehavior.cs:19032`）；`EnsureActiveRound` 在已有回合时返回原回合（`:6765`），回合解析也只检索唯一活动回合与完成历史（`:9695`）。本需求无法靠调用现有入口自然满足。

底层需提供“从明确外交安排创建独立新回合”的能力，并返回可追踪的回合 ID。请求应包含安排 ID、AI 发起统治者与王国、外交对象、动作、约定条件、交涉来源和允许公开的材料；相关旧回合只作关联，不自动并入。请求重试必须返回同一个创建结果，不重复建回合；这与玩家重复交涉是否算新安排的玩法决定是两回事。

该能力必须创建独立事件，并允许按回合 ID 继续生成根宣言、送达、回应及执行；不能复用、覆盖或关闭其他活动回合，也不能等待它们结束才创建。创建事件不等于正文已经生成或外交行动已经执行，正文请求仍需遵守 LLM 调度预算。玩家为国王并已与 AI 国王口头谈妥条件时，正式提案由 AI 国王发起，玩家自行正式接受。

本任务定义上述接入语义，不实施多回合存储、全局调度或路由重建。

## 提案归属设计

玩家可以劝 NPC 统治者接受其他国家的提案，玩家不必是提案的任何一方。实际接受者仍必须是该原案的受案国家及其有权统治者，不能由玩家或 NPC 替第三国接受。

现有源码没有独立 OfferId，正式原案以 `SourceDocumentId + SourceActionId` 定位，并从所属回合或源文档得到 RoundId。`TryResolveUniqueOpenProposalForRound`（`WorldDiplomacyBehavior.cs:3624`）与玩家公文原案协调入口（`:4603`）已具有单回合内唯一匹配思路；接受执行也不能在多个候选或失效原案中随意选择。未来应将它扩展为按有权回应者查询的多回合原案目录，而不是按国家组合挑一个活动回合。

归属顺序：

1. 仅讨论或考虑：记录交涉，不产生正式行动。
2. 明确接受既有原案：定位具体源公文及其中动作，校验受案方、原案未决状态和约定条款，向其所属回合提交正式回应。玩家与该回合的关系不影响原案归属。
3. 明确提出新的外交事项或不同条件：创建新回合；相关旧回合只作来源关联，不因国家相同而并入。
4. 多个原案无法唯一匹配：NPC 在交流中追问具体来源、日期或条款；不能任选最新、不能用新回合替代歧义处理。
5. 原案过期、已答复或失效：不能伪装成有效接受，也不能静默重建原案；需明确提出重开交涉才能成为新事项。

LLM 只能从本轮给定的候选原案中选择引用，实际归属由代码根据正式原案身份确定。生成、发布与执行前再校验引用和世界状态，防止另一回合已经改变战争关系后仍执行旧条件。请求重试不重复建回合、不重复应用外交效果；并存回合中的世界状态协调属于底层任务，本功能要求它提供有效性校验和带回合身份的结果。

人物知识也要校验：当前 `GetKnownDocumentIdsForHero`（`:10702`）已有传播、贵族通信与王庭范围。原案尚未送达时，玩家转述不能直接被视为正式提案已送达或内容已核实；应由既有传播或展示入口使人物获知真实原案，或承接转述后核验。玩家作为第三方劝说时，正式回应作者是受案国家的国王，正式对象是提出国；玩家不是因此成为协议主体。

实现时按受案王国、外交种类、原案状态索引查询，再按知晓范围过滤；在交涉请求时获取有界候选，避免逐帧遍历全部回合和公文。候选过多时不能截断后伪称唯一。
