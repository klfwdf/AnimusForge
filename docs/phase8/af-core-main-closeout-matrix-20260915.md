## 3. 内部接口稳定：不是只固定方法名

1. 同 DLL 的制作组贡献接口保留 typed `internal`，不改成对外协议；现有13方法/31调用点与ref/out/异常透传测试继续作为门槛。
2. 制作组调用主体所需的核心服务接口也要明确输入、结果、线程、生命周期、失败语义；不能仅有“AF调用制作组”的ports，就宣称双向模块接入全部完成。
3. 对话/LLM/Prompt/标签/记忆可以按需求修改真实实现，但必须保持约定行为与数据所有权。内部演进有接口对照测试，跨版本公开变化有迁移版本。
4. 同一套主体owner与权威提交，不为团队/子MOD分别创建缩水pipeline、独立记忆或新动作执行器。
5. 稳定性验收至少包括：签名、参数/返回/ref/out、异常/取消、主线程资格、owner失效、只提交一次；必要时运行旧编译客户端，而不仅仅重新编译新客户端。

## 4. 外部三渠道：已明确必交，尚未实现完

| 能力 | 首版收尾要求 | 现状 |
|---|---|---|
| Native | 可提交当前合格对话请求，取得正文与真实完成状态，支持关联/取消/晚结果拒绝 | 旧ForExternal调用面存在；版本化SDK提交尚未开放 |
| Scene | 可向当前合格Mission对话入口提交，保留参与者/接力/旁听/唯一后处理与退场隔离 | 不能把Native请求套个Scene枚举冒充完成；版本化提交尚未开放 |
| Courier | 明确发信/回信/来信请求及完成阶段，保留原送达时机与资产/事实处理，不提前提交 | 现有宿主入口不是通用public SDK；版本化提交尚未开放 |
| 共用契约 | 有界不可变DTO、AF生成的请求关联ID、版本/能力探测、明确拒绝/忙碌/取消/超时/部分失败/完成状态 | Api.V1目前只读，不能把CatalogRead当作三渠道开放 |
| 独立子MOD验证 | 独立DLL编译/实际加载，正确与不匹配版本，取消/重复请求/换存档/Mission结束；核心更新后旧客户端不崩 | 本轮旧编译客户端仅验证现有协调器ABI，不等于三渠道SDK已完成 |

- 公开接口不暴露Hero/Agent/Behavior、可变内部对象图或凭据；身份由宿主真实上下文校验，不能让调用方随意拼session绕过限制。
- 单独ActionExecute、MemoryWrite和任意扩展注册不是本次三渠道确认的替代品；不能先开放这些旁路来绕过缺失链路。
- 只有真实完整路径和候选测试落地后，才把相应能力从NotSupported改为Available；**不是将只读范围永久保留作为完成标准**。

## 5. 外域边界与删除纪律

政策/宴会/GCCZ等业务算法、数值、事件状态机、提示词和业务存档不搬到主体；只维护AF侧合法接缝及缺失/关闭/异常时的回退。排除其玩法验收不意味着可以删除它们现有调用或损坏模块装配。

旧代码的每个符号只能归入：已迁移新owner、薄引擎适配、必要Saveable/ABI兼容、明确外域保留。只在替代路径真实接线并有行为证据后删除，不按文件名包含Legacy或行数直接清仓。用户文件/历史引用材料继续受保护。
