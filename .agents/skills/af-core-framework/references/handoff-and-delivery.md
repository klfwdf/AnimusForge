# 代码坐标、覆盖状态与交付

## HANDOFF 要记录的有效信息

使用适合本次任务的简明形式，但不要遗漏：

- 当前源码提交、工作分支/远端目标、总体阶段；不要把“本轮完成”写成“整个项目完成”。
- 每个重要变更的 `path:start-end`、类/方法名、核对所用提交；附责任说明、实际调用者/渠道和关联验证。行号随改动更新，不能猜测或只靠旧 HANDOFF。
- 对主体功能调整写明“原行为 → 新要求 → 实现/配置入口 → 默认/兼容 → 验证”。接口稳定不意味着禁止调整主体功能。
- 分清 `已接线并局部验证`、`混合新旧/仅部分覆盖`、`未迁移仍在运行`、`本轮不处理的模块业务`、`设计但未开放`。实际状态按证据更新，不用“新文件/旧文件”代替功能验收。
- 被替代的代码删在哪里；保留旧入口的实际调用/ABI/存档原因。标明测试替身，不给离线 PASS 贴 LIVE 标签。
- 下一步与回滚点，允许/未允许的推送、部署、存档操作和自动化状态。

示例字段（不是写死某个函数）：

| 能力/有意变化 | 位置与符号（源码 commit） | 真实入口及 owner | 已验证 / 未覆盖 |
|---|---|---|---|
| 本次能力 | 核实的相对路径、一基行号、方法名 | 调用链和权威提交者 | 原行为/新需求用例及实机缺口 |

## 与 GitHub 旧版本隔开

- 将获准的框架工作放在专门重构分支；主分支和其他成员分支不顺带覆盖。
- 发布前 `fetch` 并核对目标 remote/ref/祖先关系，记录旧远端基线及本次范围。分叉或未知新增提交时停止，不能擅自 merge/rebase/reset/强推。
- 源码里的未迁移部分用代码范围图/符号索引标界，不为目录整齐重命名 Saveable 类型、挪动整个 owner 或建立第二份参与编译的 legacy 实现。
- 只有已验证覆盖的符号才标为本轮接入；本次 diff 没改的代码不等于不存在、已废弃或已完整验收。

## 只留本地文件的 Git 陷阱

`.gitignore` 不会让已经提交的文件从历史消失。用户说“不上传”时检查目标文件在待推送祖先中是否出现；先删除再推仍可能上传历史。

优先在尚未提交时精确排除。若文件只存在未推送本地提交中，保留原本地历史和文件，选择不含它的最后安全祖先创建干净交付分支，移植所需源码/文档而不引入排除文件。核对树差异、测试需要的历史基线可达、用户改动未混入，再普通快进推到获准的远端。不要为了排除一份文档重写共享历史；已在远端出现时如实告知，后续清历史另需授权。

发布前同时检查文件树和待推送提交历史，并消除上传文档中对本地专用文档的必需链接。对外发总/专题 HANDOFF，本地简明版不参加提交。最终用远端 ref 核对实际发布提交；不要把 dry-run 或本地 commit 当 push 成功。
